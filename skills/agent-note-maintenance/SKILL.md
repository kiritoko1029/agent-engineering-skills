# Agent 决策笔记维护

让活跃笔记继续帮助作决定，让历史记录保留当时的理据。整理的目标是明确现行约束及其来源，不是减少到某个文件数。

## 确定范围与当前依据

先读项目现有笔记、归档和链接约定。局部替代只检查同主题记录及其入链；用户明确要求全库审计时才遍历整个库。用当前代码、配置、测试、文档和较新笔记确认现状，不能仅凭文件日期判断过时。

没有既有约定时采用：

```text
.agents/notes/{proposed,implemented,rejected,archived}/<category>/YYYY-MM-DD-topic.md
```

保留已有分类与文件日期，不为整理而重建分类体系。建议把 `archived` 视为默认追加的历史区：新增历史快照，通常不改写已归档内容；这是默认维护策略，不强制项目采用永久封存、哈希清单或特定校验器。

## 按未来决策价值处理

| 情况 | 处理方式 |
| --- | --- |
| 已实施，仍约束未来工作 | 保持活跃；例如所有权边界、持久化或协议语义、安全规则、负面保证、再次引入的条件。篇幅短或年代久不影响价值。 |
| 已实施，只有现行事实过时 | 核实后原位更新路径、名称、默认值等事实，保留决定和理据。不要在正文堆叠每日变更流水。 |
| 已实施，决定已完成且不再指导后续工作 | 可归档为历史；例如已退出系统的一次性适配细节。是否仍有兼容路径、持久化数据或未解风险要按实际情况判断。 |
| 新决定完全或部分替代旧决定 | 新建或使用继任笔记，双向链接并标明替代范围。旧记录独有的备选方案、代价和未解决条件仍应可找到；部分替代不能把剩余约束一起归档。 |
| 提议仍未决 | 保持提议状态，注明缺失证据或待决问题。记录提议不等于获得实施许可。 |
| 提议已被明确否决或证据表明前提已失效 | 写清否决或失效依据后转入 `rejected`；缺乏进展本身不是否决理由。 |
| 被否决的方案仍容易被重提 | 保留能解释否决原因的记录；低价值拒绝记录可列为后续整理候选，不因审计而自动删除。 |

年龄、字数、修改频率只适合帮助定位候选，不能单独决定归档。拿不准时保留活跃状态并报告具体不确定性，不制造已裁决的结论。

## 归档而不抹去理据

默认归档对象是已完成、未来指导价值低的 `implemented` 笔记；其他状态沿用项目已有规则。没有明确结论的提议不靠移入归档区掩盖状态。

执行归档时：

1. 确认仍在使用的规则已有可定位的当前依据；必要时先补到活跃笔记。完整保留原问题、决定、真实备选方案与后果，不用一句“已过时”取代原文。
2. 将记录移动到 `archived/<category>/`，保留原始文件名与原状态，增加 `Archived: YYYY-MM-DD`，并明确“历史记录，不代表当前行为”。项目已有归档格式时按其处理。若确有配套文件，按实际关联一并处理；不生成项目原本没有的翻译或 sidecar。
3. 搜索活跃文档的入链：描述现行行为的链接改指当前依据；引用历史的链接改指归档地址。检查移动导致的相对路径变化，必要的机械修复在本次归档内完成，避免链接悄悄指向另一个对象。
4. 检查实际改动的元数据、关联文件和链接；有适用的文档检查器时运行它。归档不是运行全部应用测试的理由，也不要宣称未检查的历史出链全部有效。

归档后的内容可能有意落后于代码；当前事实应在活跃记录或当前文档中维护。需要重新讨论已归档决定时，新建活跃条目并引用历史。默认不批量更新归档中的旧路径、格式或过时术语；纠错或恢复遵从用户任务与项目历史保存规则，并留下更正的来由。

本技能的整理和归档流程不删除原有记录。只有用户明确要求删除时才进入删除处理：先确认影响范围、保留仍有用的独特理据并修复入链。不要把原文仅存在于 Git 历史视作已在现行文档保留了理由。

## 交付结果

给出本次范围、保留或事实更新的活跃记录、归档记录、继任关系和状态变化；每项实质性处理附简短理由。单独说明边界案例、缺失证据和实际运行的检查。无需按固定栏目凑齐零项统计，也不为满足整理配额创造改动。
