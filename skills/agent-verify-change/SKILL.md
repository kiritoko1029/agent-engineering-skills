# 按变更面选择验证

用最小且充分的证据支持变更结论。遵守仓库规定的必需检查，额外检查由受影响的行为、接口和执行入口决定，不为每次小改动建立全套测试仪式。

## 确认要证明的版本

- 确认仓库、分支、目标提交和比较基线；有远端审查对象时核对其实际基线。
- 检查提交差异、暂存、未暂存和相关未跟踪文件，避免遗漏即将交付的修改。
- 阅读测试配置、包脚本、构建入口、CI 工作流及适用的本地检查要求。
- 记录关键环境条件：运行时、平台、生成产物是否最新及必要服务是否可用。

可用 Git 命令辅助读取状态与差异，但使用当前仓库的真实命令和分支。不要猜测项目必然有某个测试框架、脚本或基线分支。

## 把变更映射到证据

先列出受影响行为或契约，再选择对应检查。文件路径筛选只是线索；配置加载、反射、子进程与构建入口可能超出静态依赖图。

| 变更面 | 优先考虑的证据 |
| --- | --- |
| 局部运行逻辑 | 拥有该行为的测试文件或聚焦场景 |
| 共享接口、类型或协议 | 必需类型检查及受影响调用方测试 |
| 公共导出、构建、打包、命令或工作线程入口 | 构建与实际产物入口的最小运行验证 |
| 用户或模型可见文本、格式、提示与诊断 | 对应输出断言、快照或实际入口场景 |
| 配置、动态加载、注册机制 | 使用真实配置或组装方式的集成检查 |
| 文档与技能说明 | 适用的格式、链接或技能验证，加人工核对所述行为 |
| 资源、异步测试或 CI 配置 | 针对隔离、并发、恢复与清理完成的证据 |

低影响且可逆的修改可以用已有检查或直接核对完成。新增测试应检验可观察行为或真实回归，避免仅匹配实现形状。

## 覆盖率和检查范围

测试选择与覆盖率选择是两件事。需要覆盖率时，明确所选测试能够证明哪些受影响源文件，并沿用项目的实际阈值。

- 不默认要求 100% 覆盖率，也不降低已有阈值来隐藏失败。
- 不使用“无测试也成功”之类选项替代应有的行为证据。
- 不因单个聚焦测试未覆盖整个包，就机械补跑全仓库；检查是否应补相关测试或修正合理的源范围。
- 不能排除确实受影响的文件来制造绿色结果。
- 覆盖率通过只能表明执行范围，不证明断言覆盖了正确的业务结果。

## 执行一次，保留有效结果

记录命令、版本或工作区状态、结果与关键限制。先执行能最快区分问题的必需或聚焦检查；独立且不争用资源的检查可并行。

以下变化可能使旧证据失效：被测代码或调用契约变化、生成产物重建改变行为、基线合并引入交互、测试配置或相关运行环境变化。只重跑被这些变化影响的检查。

提交、推送或交付这一动作本身不使此前结果失效。已知钩子会执行的检查无需为了重复确认而提前再跑一次，但仍应核对钩子结果及其自动修改。

全套本地测试适用于用户明确要求、广泛跨模块变更，或诊断结果表明较窄范围不足以覆盖风险的情况。CI 的完整矩阵不能自动替代本地必需证据，局部通过也不能代替完整矩阵。

## 处理失败与缺失条件

出现失败时保留原始失败信号，区分代码、测试、环境与外部服务问题。用最小补充证据确认原因，修复授权范围内的问题；不要先宣称“环境问题”。

检查缺少凭据、平台、依赖或服务时，说明缺失条件和未覆盖的行为。不要打印凭据，不把未执行、跳过、重试后成功或等待中的检查合称“全部通过”。

如果原任务包含发布或推送，相关必需检查未通过时先解决或说明阻碍。验证技能本身不授予绕过钩子、改写历史或发布的权限。

## 报告

简要列出实际执行的命令与结果，并说明这些结果覆盖了哪些行为。按观察分别标记通过、失败、跳过、未执行和等待中；若依赖重试才成功，注明次数和首次失败。

只保留会影响用户判断的限制，不罗列与本次变更无关的假设风险。所选证据已充分且通过后结束验证；只有新改动、失败或未解问题才扩大范围。
