# 维护可用的工程文档

让读者找到自己需要的操作或事实，并知道成功、失败和限制是什么。保留实际约束，删除只对当次编写会话有意义的叙述。

## 确定文档的职责

从请求、当前差异或指定页面确定范围；缺少精确路径时先查找相关文件，不自动审计全库。

| 内容 | 优先归属 |
| --- | --- |
| 项目是什么、最短上手路径 | 根 README |
| 完成一项任务所需的步骤 | 操作指南 |
| 参数、返回值、错误与支持范围 | 对应组件或接口参考 |
| 非显然的时序、所有权、局部不变量 | 临近代码的注释 |
| 为什么这样设计、备选方案与代价 | 决策记录 |
| 本次完成什么、检查结果、后续入口 | 工作日志 |
| 故障经过、影响和预防 | 事故复盘 |

沿用项目已有结构。一项事实有明确的维护位置；其他页面简述并链接。调用处不可缺少的安全使用条件可以局部重复，不为消除重复而移走必需信息。

## 先核实，再写

阅读文档的代码实现、测试、配置或生成源；既有文档和旧决策不是当前行为的充分证据。

对于命令和示例，在具备条件且任务授权范围内执行最小路径，记录必要环境及可观察结果。需要外部账户、费用或写入的操作不因“核验文档”而自动获得授权。无法实测时明确写依据与未核验部分，不冒称已运行，也不删除仍有价值且有其他依据的说明。

修改生成文档的源头，再使用项目的生成器更新产物。只在项目本来维护多语言内容时同步对应段落；不要强制引入双语、等行数或配套哈希文件。

## 写作与精简

- 先说读者能完成什么，再写所需条件、操作、预期结果和常见失败的处理。完整参数表放在参考页面。
- 改写前识别主体、动作、条件、时序、必须/可以/禁止、例外、失败与副作用，确保精简后仍完整。
- 将“如上轮讨论的第 4 点”替换为仓库内可定位的事实或有效引用。注释解释非显然约束，不复述每条语句。
- 当前使用指南描述当前行为；迁移指南、版本说明、事故复盘和决策记录可以保留必要历史。不要把“旧连接”这样的运行时概念误判成历史叙述。
- 保留真实的不确定性、度量条件、兼容承诺和限制，不把提议润色成已实现功能。
- 页面过长时按读者任务和内容归属拆分，不用统一字数上限删除必要信息。

可按 [操作指南模板](assets/task-guide-template.md) 起草新指南，按文档实际需要删减。

## 验证与结果

检查移动或重命名页面的入站链接、相对路径、导航和生成关系。在项目已有检查中选择相关 Markdown、链接或文档构建检查。

若改的是提示词、错误信息、CLI 输出或界面字符串，将它视为可能影响行为的修改，执行相应验证；普通文字润色不授权接口重命名。

报告修改范围、重要事实修正、实际执行的验证和未验证事项。仅审阅请求输出问题，不顺便改写文件；已要求修正文档时直接完成明确的修正。
