# 有依据地减少复杂度

寻找能删除、合并或降低维护成本的真实候选项。先证明复杂度的用途与成本，再决定保留、改造或移除。调查请求交付候选方案；实施请求在已授权范围内完成修改。

## 建立上下文

阅读适用仓库说明、模块边界、公共契约和相关决策记录。标记仍受支持的平台、外部扩展点、持久化格式与兼容性要求。

现有测试和历史记录是证据，不是不可更改的真理；明确的产品能力和外部承诺也不能仅因本仓库缺少调用而认定无用。

## 寻找值得调查的候选项

- 公共方法、配置项、事件、包或辅助层缺乏当前用途。
- 两份状态、事件或缓存长期维护同一个事实。
- 每个实现都承担某个接口成员，但生产消费者从未使用它。
- 大量回滚、就绪信号和状态标志重复描述同一生命周期。
- 支持代码造成独立发布、依赖或构建负担，却不需要独立边界。
- 自行实现的基础设施可由运行时内置能力或合适依赖覆盖。
- 文档和注释重复实现细节，增加变更时的同步负担。

优先调查维护成本高、影响路径清晰的部分。未使用符号扫描适合发现线索，不能单独证明删除安全。

## 证明消费者和约束

1. 用 `rg` 搜索符号、方法、配置键、事件名、包名及序列化字符串。
2. 将结果分为生产调用、测试、文档，以及尚待确认的示例或脚本。
3. 阅读实际调用点，再检查反射、注册、配置驱动调用、插件、命令入口与构建产物。
4. 检查公共导出、外部使用约定、旧数据读取、迁移和兼容分支。
5. 确认现有测试保护的是仍有价值的契约，还是仅保护候选实现本身。

结论应写成“在已检查的生产范围内未发现调用”，除非证据确实足以支持更强断言。测试是唯一引用，并不自动意味着功能可删除。

## 检查状态、信任与生命周期

对每个复制、冻结、校验、缓存或防御分支，说明数据来源、下一位所有者和保护的实际边界。跨进程、持久化、配置或不可信输入的校验不能因内部调用有类型就移除。

对复杂异步流程画出所有权与转换关系，将每个标志、等待和清理器对应到独立事实。仅合并确实重复的机制，保留发布前回滚、终态竞争、异常隔离和等待清理完成的必要语义。

## 衡量净收益与反例

对每个候选项记录：

- **现状与证据**：拥有者、生产消费者、当前负担和相关位置。
- **最小方案**：具体删除、合并、私有化或迁移哪些表面。
- **净成本变化**：实现、测试、文档、构建和依赖总负担如何变化。
- **最强反例**：什么当前场景仍需要原设计；能否从实际调用或契约证明。
- **放弃的能力**：行为、扩展性、兼容性或可诊断性有什么变化。
- **验收条件**：可观察的最终状态与针对性验证。

评估替换依赖时，核对运行环境、维护状态、许可证、依赖体积、剩余适配代码与缺失语义。把同一复杂度搬进包装层不算收益；内置能力也须覆盖实际契约。

遇到生产调用、保留理由或当前兼容需求时，修正方案或标为需要产品取舍。若收益过小、证据不足或牵动无关模块，保留现状并说明原因。

## 实施与交付

- 广泛调查可以按独立领域并行，但每个候选项都应有自己的证据。
- 先交付少量可信候选；不要为满足数量制造建议。
- 实施时同步清理确实失效的导出、配置、生成项、测试和文档。
- 保留非显然的契约与关键决策理由；删除重复实现叙述时让信息归到其维护位置。
- 仅在变更使某份记录过时时更新该记录，不扩张成全仓库文档整理。
- 使用受影响契约的现有检查；增加测试只为证明行为或删除条件，不为复述新实现。

最终说明减少了什么、为什么安全、牺牲了什么、执行了哪些验证，以及仍未确认的外部消费者或兼容风险。
