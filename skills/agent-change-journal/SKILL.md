# 开发工作日志

让下一位开发者或 Agent 能判断工作进度、找到改动和验证依据，并继续下一步。日志记录结果与未完成事项；涉及长期设计取舍时链接决策记录，避免把两者写成同一份文档。

## 收集真实状态

1. 确定项目、这段工作的目标和记录范围。读取已有日志约定；没有约定时使用 `.agents/journal/YYYY-MM-DD.md`，日期采用项目或用户时区。
2. 查看任务上下文、工作区差异和相关提交。Git 项目可用 `git status --short`、`git diff --stat`、`git diff`、`git diff --cached`；日志范围由任务决定，不把整天所有人的提交都归给当前 Agent。
3. 从实际执行记录整理检查命令、运行目录、结果和限制。Git 历史不能证明测试已执行；没有记录就写“未验证”。
4. 如果文件已存在，只追加这次任务的小节或更新同一个任务的小节，保留其他任务与作者的内容。多人同时工作时优先采用项目已有的每任务文件约定。

## 写可接续的记录

根据 [日志模板](assets/journal-template.md) 保留有内容的部分：

- **目标与状态**：完成、部分完成、阻塞或已放弃，说明当前可用结果。状态对应开发目标；若本次只整理记录，分别说明记录任务和原开发目标的状态，不能以“日志已写完”代表功能已完成。
- **实际改动**：写行为或结果的变化，以及相关文件；不要逐条复述工具调用。
- **验证证据**：准确命令、必要的环境、退出结果或观测结果。区分通过、失败、未运行和因条件缺失而跳过。
- **决策与限制**：简述影响接续的选择并链接已有决策；记录可复现失败、覆盖缺口和剩余限制。
- **接续入口**：下一步具体动作及完成判据。若已完成且无待办，明确写无。

优先用相对 Markdown 链接指向实际存在的文件。尚不存在的文件用行内代码标明“待创建”；不要制造可点击但无效的证据链接。引用提交时使用真实提交标识；未提交工作写明未提交，不以当前 HEAD 冒充改动版本。

记录结论和可核验的简要依据，不保存对话全文、内部推演、秘密值或大段原始日志。大体积观测资料放在项目允许的位置并链接；临时文件标明保留期限或易失性。

## 恢复工作

按任务名、受影响模块和日期检索，先读最近的相关任务小节及其直接引用。再用当前代码、工作区差异和测试确认状态：历史上通过不表示当前工作区仍通过，历史“待办”也可能已被后续工作完成。

从记录中的最小未完成动作继续。遇到失效路径或状态漂移，在新记录中纠正并指出当前入口；不要将历史记录悄悄改成今天的事实。

## 交付

回报日志路径、当前状态和重要的下一步即可。只有本次任务结束或显式总结时才写入，不逐轮对话落盘，不制造空白日报，也不自动创建定时任务。
