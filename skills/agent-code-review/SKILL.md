# 以证据为中心的代码审查

目标是找出会影响现有使用场景的缺陷，让作者能根据具体触发条件复现并修复。优先关注正确性、生命周期、安全边界和承诺的行为；少量可靠发现比大量风格意见更有用。

## 确定审查对象

1. 确认用户要审查的分支、提交、补丁或工作区，以及对应基线。
2. 阅读适用的仓库说明、受影响模块契约和相关决策记录。
3. 查看完整差异和足够的上下文，区分提交内变更、暂存与未暂存修改。
4. 如果基线、目标提交或合并结果变化，重新界定差异，仅更新受影响的判断。

决策记录用于解释设计动机。它可能已经过时，与记录不一致本身不构成缺陷。审查说明和已有测试同样需要与当前实现核对。

## 从调用方追到执行点

对每个重要变更，建立一条可验证的路径：

`实际入口 → 调用方 → 变更点 → 状态或外部副作用 → 可观察结果`

- 阅读接口两端，确认输入、返回值、错误、取消和资源归属的约定一致。
- 搜索生产调用方、配置、注册表、动态加载和构建入口；静态引用不一定覆盖真实入口。
- 追踪拒绝条件直到真正执行操作的位置，检查直接或替代调用方是否能绕过约束。
- 公共行为变化同时核对文档、提示、诊断和用户可见输出；只要求更新被影响的契约。
- 检查保留值的权威来源和所有衍生视图，避免缓存、回放、界面与持久化状态各自成立却互相矛盾。

仅在以下问题与差异相关时深入，不把它们扩成每次审查的固定清单。

## 异步与资源生命周期

- 资源在发布或回调重入前是否已经有明确所有者。
- 初始化期间取消、等待期间销毁、重复结束和晚到回调如何处理。
- 监听、子进程、工作线程、连接和临时文件是否有完整清理路径。
- 清理是否等待拥有的工作真正结束，而不只调用关闭或取消方法。
- 多个状态标志是否表达不同事实；共享可变状态是否存在实际可达的竞争。
- 回调异常和清理失败是否能被观察，是否掩盖了原始错误。

不要凭想象加入“恶意对象”等输入模型；先确认边界是否实际接收不可信、可变或跨进程数据。

## 证据与测试

- 让断言观察输出、文件、事件、状态、退出或资源释放，避免仅检查组件自己的成功声明。
- 检查回归用例是否经过受影响的真实入口。替代组装路径可能绕过加载、导出或构建错误。
- 怀疑竞争时寻找可控的交错顺序；重复运行成功不证明竞争不存在。
- 当缺陷需要运行证据时，选择能辨别该缺陷的最小检查；绿色检查不替代语义审查。
- 区分“已复现”“由代码与调用链证实”和“仍需验证”；不把覆盖率数字当作行为正确的证明。
- 已由通过的自动检查充分覆盖的格式问题通常无需再次报告。

## 形成发现

提交发现前，尝试推翻自己的判断：是否有上游保证、不可达条件、备用路径或明确的产品选择。若只能表达偏好，降为建议或省略。

每项可行动发现包含：

- **位置**：最小相关代码位置，或跨模块问题的关键路径。
- **触发条件**：什么输入、状态、配置或顺序会导致问题。
- **实际影响**：谁会受到什么可观察影响。
- **证据**：调用方、代码路径、失败用例或运行结果。
- **严重程度**：依据影响和发生条件判断，避免只按代码外观评级。

示例：取消请求在连接初始化完成前到达时，随后创建的连接未进入清理集合；该入口会留下活动句柄。指出相关创建与登记位置，并给出受控取消场景。

若没有可靠发现，直接说明未发现可确认缺陷，并指出审查范围及尚未执行的关键验证。不要为了凑数制造问题。

## 交付边界

按原任务交付审查结果。仅审查的请求不自动扩大为修改代码、发送评论或合并变更。收到审查意见时先复核事实，再基于证据修复或解释。
