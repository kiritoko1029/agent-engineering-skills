# Agent 决策笔记

让接手者知道一个决定为什么成立、放弃了什么、何时需要重新考虑。笔记承载代码与操作文档不容易表达的理据，不复制实现清单，也不把一次会话写成设计文档。

## 先判断是否值得记录

先读项目现有笔记约定，再用相关组件名、接口名和备选方案搜索同主题的活跃笔记。通常先搜 `.agents/notes` 的非归档目录；历史问题再定向搜 `archived`。已有 ADR 或其他目录时直接沿用，不另建一套。

以下情况通常有记录价值：跨模块契约、状态或持久化的权威来源、兼容与迁移边界、显著成本取舍、安全边界、容易被反复提出的否决方案，以及有明确重新引入条件的功能移除。一个很短的决定也可能很重要。

以下情况通常不需要新笔记：拼写与格式修正、无行为变化的局部重命名、常规依赖更新、结论已被现有笔记覆盖的修复，以及只需报告完成情况的工作。若这些改动产生了新的兼容性或架构取舍，再按实际价值记录。每日做了什么、运行了什么、下一步做什么放进 `.agents/journal` 或项目已有日志，必要时链接决策笔记。

## 记录一项可追溯的决定

1. **找依据。** 结合用户要求、相关变更、测试和讨论区分已确认事实、计划与未知项。不要从一段提议推断它已获批准或已被实施；笔记本身不增加执行授权。
2. **选归属。** 同一决定的路径、符号或默认值变化，更新原笔记中的现行事实。决定或理据发生实质变化时新建继任笔记，用相对 Markdown 链接注明替代范围；旧笔记链接回继任者，不把旧结论改写成相反结论。部分替代时明确哪些约束仍有效。
3. **写取舍。** 先说明独立于方案的问题，再说明决定、真实考虑过的备选方案及其未被采用的原因，最后说明收益、代价和适用边界。没有留下备选方案记录时写明证据缺口；不要为了填模板虚构比较。
4. **给出证据。** 只保留有助于理解或验证决定的源码、测试、讨论或文档链接。测试说明区分已执行结果、已有覆盖和仍待验证的部分；不要把测试计划写成通过记录。

新项目可采用这个默认路径，已有约定优先：

```text
.agents/notes/{proposed,implemented,rejected,archived}/<category>/YYYY-MM-DD-topic.md
```

分类按项目需要命名，例如 `architecture`、`process`、`testing`，不用预建空目录或固定分类集合。文件名日期表示首次记录或提出的日期；沿用已知日期，不把推测写成历史。正文可用项目主要语言，不要求翻译配对或额外元数据文件。

## 状态要反映真实进展

| 状态 | 应说明的内容 |
| --- | --- |
| `proposed` | 问题、建议方案、真实备选方案、可观察的验收条件、风险及未决问题。已同意但尚未落实的工作仍是提议。 |
| `implemented` | 当前目标范围内已经落实的决定、实现证据、取舍与限制；若是否发布有影响，另行写清发布状态。 |
| `rejected` | 被否决的方案、否决原因与依据；保留理解当时提议所需的上下文。 |

采用默认布局时让目录与 `Status` 一致。归档记录可以保留原状态，并增加归档日期，表示历史快照。提议转为已实施时，将计划改写为实际结果，保留未完成部分的真实状态；不要仅移动文件就声称完成。

需要起草时复制并按状态精简 [决策笔记模板](assets/decision-note.md)。模板栏目是帮助表达的起点，不是每个项目的强制格式。

## 完成前

核对状态与证据是否一致、新旧记录的职责是否清楚、改动涉及的链接能否定位。移动笔记时搜索并修复活跃文档中的入链；不要顺带整理整个笔记库。运行项目已有且适用于这些文档变更的检查，报告新增或更新的笔记及尚未确认的事项。
