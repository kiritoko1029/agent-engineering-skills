# 交付相互依赖的变更

把依赖关系、每层验证结果与真实合入状态对应起来，避免用最上层的成功掩盖底层问题。此技能不绑定 GitHub、GitLab 或特定堆叠扩展。

## 建立依赖关系

读取目标平台的当前变更元数据、基线、源分支与精确提交标识，画出由下到上的依赖列表。若平台管理原生 stack，以该对象确认成员和顺序，不仅凭相似分支名猜测。

记录每层的状态、依赖、检查与未解决讨论。确认用户要求的是准备、同步，还是合入；已有授权持续有效，无需为同一动作重复询问。若只要求准备，完成本地变更、验证和可审阅结果。

局部交付须包含所选变更需要的前置层，不能跳过未合入的依赖。确有不明确且会改变合入范围的边界时，再提出具体问题。

## 同步并验证

1. 检查本地未提交工作。需要隔离时使用独立工作区，保留他人或已有修改。
2. 使用仓库已接受的合并、变基或平台 stack 流程，从最先引入问题的层修复，再传播至上层。不强制所有平台采用某一种历史策略。
3. 同步前了解工具是否会同时推送远程分支；有这种副作用时将它计入用户授权的动作范围。
4. 冲突解决后验证实际改动，不用保留“我们这边全部内容”的方式掩盖依赖差异。
5. 每层按受影响行为执行相关检查。历史重写或基线变化后，重新读取提交和平台检查状态；不能将旧提交的通过状态绑定到新提交。

已有的通过结果仍适用于完全相同且依赖未变的代码时，不为提交或推送本身重跑所有本地检查。遵守平台对当前提交的必需检查要求。

如果授权内确实需要重写远程历史，使用受预期远程提交约束的 lease，远端已变化即停止该次覆盖并重新检查。不使用无条件强推，也不在自动循环里不断刷新预期提交重试覆盖。

## 执行已授权的合入

在最终动作前刷新选定层的状态、当前提交、检查与评审要求。平台有适用的原生依赖合入能力时优先使用；没有时只沿用已经支持且能验证依赖顺序的项目流程，不模拟未知 API 或绕过保护规则。

逐层跟踪结果。进入队列、命令退出成功或请求被接受都不等于已合入；以服务端最终状态与目标分支提交为准。部分成功时准确记录已合入层、剩余层与阻塞原因，保留可继续的状态。

确认剩余变更的基线与依赖关系仍正确。只有任务包含分支清理时，才在合入完成且没有开放变更依赖该分支之后删除；不要顺便清理其他分支。

## 输出

提供简短表格：变更标识、基线、验证的提交、相关检查、最终状态。给出剩余动作和具体阻塞原因；尚未观察到最终状态时写“等待中”，不声称已交付。
